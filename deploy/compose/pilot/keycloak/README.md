# Pilot Keycloak realm (`ne-pilot`) — demo import artifact

`ne-pilot-realm.json` is a **checked-in dev/pilot demo realm** (owner dec v),
imported on Keycloak start via `--import-realm`. It is **NOT a real identity
provider**: it seeds four demo users so the loginable pilot works end-to-end
today. Real customer identity is *brokered* later (Entra ID / Okta federated into
Keycloak, which then mints local tokens) — brokering **replaces** these seeded
users. See `deploy/compose/dev/keycloak/README.md` for the brokering shape.

Every Neutron Enterprise service trusts **only the local Keycloak issuer** (C10).
The pilot issuer is `https://<hostname>:8443/realms/ne-pilot`, matching
`NE_IDENTITY_OIDC__ISSUER` on the `ne-api` service.

## Demo credentials (C12 — the ONLY sanctioned literal creds in the pilot tree)

These are documented demo credentials, replaced entirely by IdP brokering. They
are the sole exception to the pilot tree's no-secret-literal rule (owner dec v);
`test_pilot_secret_hygiene.py` does not flag JSON-quoted keys.

| Username   | Password        | Group       | Platform role (via `NE_API_*_ROLES`) |
|------------|-----------------|-------------|--------------------------------------|
| `approver` | `approver-demo` | `/approver` | approver (HITL approval)             |
| `steward`  | `steward-demo`  | `/steward`  | steward (flywheel review)            |
| `ops`      | `ops-demo`      | `/ops`      | ops (audit read)                     |
| `meridian-frontline` | generated by `ne demo up` | `/meridian-frontline` | none (restricted Meridian reader) |

The Meridian credentials are demo-only. On a fresh realm import, `ops` is the
allowed owner and `meridian-frontline` is the restricted same-department
principal. The frontline account has no imported credential. The hardcoded
mapper below gives both the exact existing `department: engineering` claim.
After reconciling both principals' exact persona/entitlement groups, `ne demo
up` installs generated non-temporary owner and restricted credentials and
records them only in the mode-0600 `demo-credentials.json` file. The import file
itself is skipped when the realm already exists, as documented below.

The seeded group names (`approver`/`steward`/`ops`) match the `ne-api`
`NE_API_APPROVER_ROLES` / `NE_API_STEWARD_ROLES` / `NE_API_OPS_ROLES` env exactly:
`require_role` checks `Principal.groups` verbatim against those role sets, so no
realm roles are needed — group membership alone resolves the fail-closed
pre-checks in NE-104b/c.

## The `ne-console` public client

- **Public PKCE (S256) SPA client** — `publicClient: true`, no client secret
  (a browser cannot keep one). `standardFlowEnabled` (auth-code + PKCE) is the
  real browser login path.
- `directAccessGrantsEnabled: true` — **demo/CI only.** It enables the browserless
  password-grant login used by the sealed-netns Phase A e2e
  (`test_password_grant_login_end_to_end`). Turn it **off** once real IdP
  brokering lands (the browser auth-code flow does not need it).
- `redirectUris` use the `${NE_PILOT_HOSTNAME}` placeholder, resolved at import by
  Keycloak's documented startup-import env substitution (see below), ending in
  `/auth/callback` (the console default `${origin}/auth/callback`). `webOrigins`
  is `["+"]` (echo the redirect origins for CORS).

## Claim mappers

- **`ne-groups`** — `oidc-group-membership-mapper`, emits `groups` with
  `full.path=false` (the claim is `approver`, not `/approver`).
- **`ne-console-audience`** — `oidc-audience-mapper`, adds `ne-console` to the
  access-token `aud` (matches `NE_IDENTITY_OIDC__AUDIENCE`).
- **`ne-department`** — a **hardcoded** `department: engineering` claim
  (`oidc-hardcoded-claim-mapper`). SPEC §11 A1 requires the realm to emit
  `department`; a per-user *user-attribute* mapper risks KC-24+
  unmanaged-attribute-policy import fragility, and all three demo users sharing
  `engineering` is fine for the pilot. Real IdP brokering supplies per-user
  departments from the customer directory.

## Import mechanics

The realm is imported at container start via `start --import-realm`; the JSON is
mounted read-only at `/opt/keycloak/data/import`. **Import is SKIPPED for a realm
that already exists** — so editing this file does NOT re-apply to an
already-initialized Postgres. To apply edits, drop the Keycloak schema/database
(or bring up on a fresh `pg-data` volume), then `ne up` again. CI is immune: each
no-egress run starts from fresh volumes.

### Image rollback does not roll back the database

Downgrading Keycloak is unsupported: an older image starts anyway against a
26.7-migrated database, but it runs on a schema it does not know. On startup
it logs
`WARN [org.keycloak.storage.datastore.DefaultMigrationManager] Possibly
incorrect state of migration. You are trying to run server version
'<older>' against database, which was already migrated to newer version
'<newer>'.` and continues serving on that schema. Rolling the pinned image
back — a `git revert` of the pin plus a redeploy — therefore does not roll
a 26.7-migrated database back. Rolling back requires
restoring the `keycloak` database from a backup taken before the newer image
first started. Take that backup before deploying any Keycloak pin bump.

### Duplicate-group 409s log a harmless Hibernate WARN

`ne demo up` provisioning (`tools/ne-cli/src/ne/cli/demo/live.py`) issues 23
`POST /admin/realms/ne-pilot/groups` calls per invocation (covering 17 unique
demo group names) and treats `409 Conflict` as success. On a freshly imported
realm, 5 of those 23 POSTs return `201` and 18 return `409`; a re-run against
an already-provisioned realm returns `409` on all 23. Each conflicting `409`
logs one server-side `WARN [org.hibernate.orm.session] HHH90010101: Closing
shared session with unprocessed transaction completion actions`; the HTTP
status, response body, and realm state this produces are unchanged from the
previous release line. The WARN is harmless and expected — it does not
indicate a failed group creation or a state change.

### `${NE_PILOT_HOSTNAME}` substitution

Keycloak resolves `${VAR}` placeholders from environment variables during
`start --import-realm` (keycloak.org/server/importExport). The `ne-api` service —
and the `keycloak` service itself — receive `NE_PILOT_HOSTNAME` from the config
bundle (`ne up --bundle`); it substitutes into the `redirectUris`. If substitution
ever failed, only the *browser* redirect URIs would be affected (the CI
password-grant e2e does not exercise redirect URIs); the guardian asserts the
placeholder shape statically.

## Entra ID broker (`entra` identity provider — disabled by default)

The realm carries a real, disabled-by-default `identityProviders` entry
(alias `entra`) plus a three-group `identityProviderMappers` scaffold
(`approver`/`steward`/`ops`), promoted from the dev realm's documented
placeholder into a per-customer-activatable pilot artifact.

### Alias is pinned

The broker callback is `/realms/ne-pilot/broker/entra/endpoint`. The
Terraform-registered redirect URI
(`deploy/terraform-eks-entra-broker/main.tf:37`) hardcodes the `entra`
segment, so the identity provider's `alias` must **never** change — a
different alias produces a green-CI artifact that fails only at real token
exchange with Entra. This is pinned by a structural test:
`packages/ne-identity/tests/test_realm_config.py::test_pilot_entra_alias_matches_terraform_redirect`,
which derives the expected alias by reading the `.tf` files at test time
rather than hardcoding both sides.

### Secrets

`clientSecret` / `clientId` / `tenantId` are the `${NE_PILOT_ENTRA_BROKER_CLIENT_SECRET}`
/ `${NE_PILOT_ENTRA_BROKER_CLIENT_ID}` / `${NE_PILOT_ENTRA_TENANT_ID}`
interpolations, resolved by the same Keycloak startup-import env
substitution documented above for `${NE_PILOT_HOSTNAME}`. A `${...}`
interpolation is C12-clean by the same guardian rule that already permits
`${NE_PILOT_POSTGRES_PASSWORD}` — the earlier "no broker placeholder" note
was guarding against a *literal* placeholder (like the dev realm's
`REPLACE-PER-CUSTOMER`), not a `${...}` interpolation.

**Shipped behavior:** `ne up` resolves the three names from the SecretStore
path `pilot/entra-broker` (fields `tenant_id` / `client_id` / `client_secret`
— the `OPTIONAL_SECRETS` map in `tools/ne-cli/src/ne/cli/pilotcfg.py`) into
the Keycloak container env. An **absent** path writes zero
`NE_PILOT_ENTRA_*` keys into the runtime env file; the three matching
compose keys use a **null-value pass-through** declaration (the same
NE-087 `NE_REBAC_*` idiom, `deploy/compose/pilot/compose.yaml`), which
**OMITS** them from the keycloak container env entirely when they are
unset in `--env-file` — never a `${...:-}` empty-default (that would
instead *define* the vars as empty strings inside the container). This is
verified two ways, not asserted: a rendered `docker compose config` diff
(both states — see the NE-BEW-INJECT PR body) showing the three keys as
`null` when absent, and the `no-egress` CI workflow, which performs a real
`ne up` against a bundle with no `pilot/entra-broker` path and is the only
thing that proves Keycloak's `--import-realm` tolerates the result. A
**present** path with one or more fields **missing OR empty-string** fails
`ne up` loudly (empty-string is treated identically to missing — see
"Enable procedure" below), naming the affected env vars (names only, never
values, per C12).

### Group overage — fail-loud, and why

Microsoft Entra does **not truncate** an oversized `groups` claim — past
**150 group memberships (SAML) or 200 (JWT/OIDC)** it **omits the `groups`
claim entirely** and instead emits an overage indicator
(`"_claim_names": {"groups": "src1"}` plus `_claim_sources` pointing at the
Graph `getMemberObjects` endpoint; implicit-flow tokens instead carry
`hasgroups: true`). Keycloak's OIDC broker does not resolve that pointer, so
a naive mapper sees no `groups` claim at all and the user JIT-provisions with
**default roles only** — a silent under-authorization. The population most
likely to exceed the limit is the long-tenured admin/privileged population,
so this failure silently strips access from exactly the users who matter
most, and it looks like an ordinary "my access is broken" ticket, not a
security event.

**Two-part fix, both required:**

1. **Reduce the probability.** The Terraform-registered app now sets
   `group_membership_claims = ["ApplicationGroup"]` (both
   `deploy/terraform-eks-entra-broker/main.tf` and
   `deploy/terraform-azure/modules/identity/main.tf`) instead of
   `["SecurityGroup"]`. Only groups **explicitly assigned to the broker app
   registration** are ever emitted in the `groups` claim, so the emitted set
   is small, bounded, and intentional — overage becomes structurally
   near-impossible for a correctly-configured customer. This is why step 0
   below (assigning platform groups to the app) is **REQUIRED**, not
   optional: with `ApplicationGroup`, an unassigned group is **never**
   emitted, so skipping that step makes every brokered login arrive with
   zero groups — it will look like the fix itself is broken in the field.
2. **Fail loud on the residual case.** (1) reduces but cannot eliminate
   overage (a customer can still under-assign, or a user can still cross the
   app-assigned-group limit). The realm carries a marker realm role
   `entra-groups-overage`, granted by two `oidc-advanced-role-idp-mapper`
   entries on the `entra` provider — one matching the `_claim_names.groups`
   overage indicator, one matching the `hasgroups: true` implicit-flow belt
   — both `syncMode: FORCE` (a user who drops below the limit is
   automatically un-flagged on their next login). The provider's
   `postBrokerLoginFlowAlias` points at `entra post broker login`, a
   CONDITIONAL flow that runs `conditional-user-role` (checking for the
   marker role) then `deny-access-authenticator` if it matches. A user whose
   token arrives with the overage indicator and no usable `groups` claim
   sees:

   > Sign-in blocked: Microsoft Entra omitted your groups claim (group
   > overage), so your platform roles cannot be determined. Contact your
   > administrator to assign your platform groups to the broker app
   > registration (Entra broker runbook, 'Group overage').

   instead of silently logging in with zero platform groups. The marker
   role is **never read by ne-identity** (token roles/`realm_access` are
   never mapped to platform roles, `packages/ne-identity/README.md`), so it
   cannot leak into platform authorization by itself — it exists solely to
   drive this deny flow.

**Operator triage:** a user reports the deny message above → verify in the
Entra portal that their platform-relevant security groups are assigned to
the broker app registration (Enterprise applications → `<prefix>-keycloak-broker`
→ Users and groups). If they are all assigned and the user is still denied,
they may be a member of enough *app-assigned* groups to exceed the token
limit on their own — reduce their app-assigned group count or route them
through the Graph-resolution follow-up (out of v1 scope, design §4.2-3).

### Enable procedure

0. **REQUIRED — assign platform groups to the broker app.** In the Entra
   portal: Enterprise applications → `<prefix>-keycloak-broker` → Users and
   groups → assign each platform-relevant security group (the ones mapped
   to `/approver`, `/steward`, `/ops` below). With
   `group_membership_claims = ["ApplicationGroup"]`, an **unassigned group
   is never emitted** in the `groups` claim — skip this step and every login
   arrives with zero groups (see "Group overage" above).

   **Migration note (brokers deployed before this fix):** if you already
   applied this Terraform root with `group_membership_claims =
   ["SecurityGroup"]`, re-apply Terraform first (moves the app to
   `ApplicationGroup`), **then** assign the platform groups per step 0
   above, **then** have affected users re-login. Skipping the reassignment
   step after re-applying Terraform will silently zero out everyone's
   groups, not just the >150-group population. If the broker was already
   **enabled on an already-initialized pilot** (import skipped — see
   "Import-skip constraint" below), the six fail-loud objects listed there
   must also be applied via `kcadm.sh`, or the migrated deployment gets the
   `ApplicationGroup` fix WITHOUT the fail-loud deny chain and the
   silent-under-authz path stays open for anyone who still overflows.

1. Populate the customer SecretStore path `pilot/entra-broker` (fields
   `tenant_id`, `client_id`, `client_secret`) **in one write with all three
   fields non-empty.** The Terraform-created
   `${prefix}-entra-broker-client-secret` contains **only** the client
   secret — do not write it alone. `ne up` treats a missing field and an
   empty-string field identically, so writing `client_secret` alone (the
   natural mid-configuration state when copying straight from Terraform
   output) leaves `tenant_id`/`client_id` unset and makes the **entire
   stack fail to start**, by design, until all three fields are populated.
   Recovery: either finish populating all three fields, or delete the
   `pilot/entra-broker` path entirely to go back to the absent-path
   clean no-op.
2. Flip the provider's `"enabled": false` to `"enabled": true`.
3. Replace the `REPLACE-ENTRA-GROUP-ID-*` placeholders in the three
   `identityProviderMappers` entries with the customer's actual Entra
   security-group object IDs (see the GUID↔platform-group table below —
   Entra emits **group object IDs (GUIDs)**, not names, in the `groups`
   claim by default, so the placeholders must be replaced with object IDs,
   not display names).

### Import-skip constraint

`--import-realm` is **skipped for a realm that already exists**
(see "Import mechanics" above). So enabling the broker on an
**already-initialized** pilot does NOT apply by editing this file alone:
either bring up on a fresh `pg-data` volume (fresh deployments and CI import
normally), or apply the FULL set below to the live realm via `kcadm.sh` (a
documented runbook step; a `ne pilot broker enable` CLI wrapper is a noted
follow-up, not v1). Applying only the provider + Claim-to-Group mappers and
omitting the fail-loud objects reproduces the CRIT this unit closes — the
`ApplicationGroup` Terraform change lands (it's API-side, not realm-JSON),
but the realm never gains the deny chain, so a still-overaged user under
this migration path silently resolves to zero groups again. The live realm
must gain **all six** objects this unit added to the checked-in JSON:

1. The `entra` `identityProviders` entry (already covered above) plus its
   `postBrokerLoginFlowAlias: "entra post broker login"` binding.
2. The three `oidc-advanced-group-idp-mapper` Claim-to-Group entries
   (`approver`/`steward`/`ops`, from U1 — already covered above).
3. The realm role `entra-groups-overage` (top-level `roles.realm`).
4. The two `oidc-advanced-role-idp-mapper` overage mappers on alias
   `entra` (`entra-groups-overage-indicator` keyed on
   `_claim_names.groups`, `entra-groups-overage-hasgroups` keyed on
   `hasgroups`), both `syncMode: FORCE`, both granting the role from (3).
5. The two authentication flows (`entra post broker login` top-level,
   `entra groups overage check` subflow) and their executions
   (`conditional-user-role` → `deny-access-authenticator`).
6. The two `authenticatorConfig` entries (`entra-overage-condition` with
   `condUserRole` set to the role from (3), `entra-overage-deny` with the
   operator-facing `denyErrorMessage`).

See "Group overage — fail-loud, and why" above for what each object does;
`packages/ne-identity/tests/test_realm_config.py` derives every link of
this chain from the checked-in JSON, so diffing a `kcadm.sh get` export of
the live realm against that file's objects is the fastest way to confirm
nothing was missed on a manual apply.

### Sync

The provider and its group mappers use `syncMode: FORCE` — a group removed
at Entra de-provisions the corresponding Keycloak group membership on the
user's next login.
